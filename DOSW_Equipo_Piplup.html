ENUNCIADO PIPLUP AquaPort MVP — 4 drones, zonas fijas, operador manual ›

Contexto: La ECI tiene 4 drones acuáticos del mismo modelo (Aqua-Ranger 100). Solo transportan muestras de agua y sensores ligeros. Las zonas posibles son fijas: Embalse Norte, Canal Central, Laguna Sur, Punto Ribereño Este y Laboratorio Hídrico. Un operador selecciona manualmente qué drone asignar a cada misión.

Flujo básico: El operador registra una solicitud de transporte (punto de partida, punto de llegada, tipo de carga) → revisa qué drones están disponibles y con batería suficiente → asigna uno manualmente → el drone ejecuta la misión por ruta predefinida → el operador confirma la entrega.

01 · Streams & Lambdas

El contexto del reto

El operador necesita consultar la flota antes de asignar una misión: ver los drones disponibles, ordenarlos por batería y saber cuántos tienen suficiente energía para operar.

El modelo que usarás

record DroneAcuatico(
    String  id,
    String  modelo,
    int     bateria,       // 0-100%
    boolean disponible,
    String  zona           // "Embalse Norte", "Canal Central", etc.
) {}

List<DroneAcuatico> flota = List.of(
    new DroneAcuatico("AR-01", "Aqua-Ranger 100", 92, true,  "Embalse Norte"),
    new DroneAcuatico("AR-02", "Aqua-Ranger 100", 45, true,  "Canal Central"),
    new DroneAcuatico("AR-03", "Aqua-Ranger 100", 18, false, "Laguna Sur"),
    new DroneAcuatico("AR-04", "Aqua-Ranger 100", 73, true,  "Punto Ribereño Este")
);

Las 5 consultas que debes implementar solo con Streams

  1. Obtener la lista de drones disponibles con batería ≥ 35%, ordenados de mayor a menor batería.
  2. Obtener solo los IDs de los drones disponibles (como List<String>).
  3. ¿Existe algún drone disponible con batería ≥ 35%? (retorna boolean)
  4. Contar cuántos drones están disponibles.
  5. Obtener el drone con mayor batería de toda la flota (retorna Optional<DroneAcuatico>).
⚠ ProhibidoUsar for, while o variables mutables externas al stream. Cada consulta es un stream distinto, de una sola cadena.

TDD para el ValidadorMision de AquaPort

El ciclo — siempre en este orden

  1. Red: Escribe la prueba. El código no existe aún — la prueba falla. Esto es correcto y esperado.
  2. Green: Escribe el código mínimo para que la prueba pase. Solo lo mínimo.
  3. Refactor: Mejora la estructura sin cambiar el comportamiento. Las pruebas garantizan que no rompiste nada.

Las pruebas primero — ValidadorMision

class ValidadorMisionTest {
    private ValidadorMision v;

    @BeforeEach
    void setUp() { v = new ValidadorMision(); }

    @Test
    @DisplayName("Drone con batería ≥ 35% puede ser asignado")
    void droneBateriaSuficiente_puedeAsignarse() {
        // ARRANGE
        DroneAcuatico d = new DroneAcuatico("AR-01", "Aqua-Ranger 100",
                                               85, true, "Embalse Norte");
        // ACT
        boolean resultado = v.tieneBateriaSuficiente(d);
        // ASSERT
        assertTrue(resultado);
    }

    @Test
    @DisplayName("Drone con batería < 35% NO puede ser asignado")
    void droneBateriaCritica_noAsignable() {

                                               18, false, "Laguna Sur");
        assertFalse(v.tieneBateriaSuficiente(d));
    }

    @Test

        assertThrows(IllegalArgumentException.class,
            () -> v.validarPuntoLlegada(null));
    }
}
